4. The offline version: Headscale

Why the Headscale run never showed this

The old code fell back to the host network on Headscale too. But there the fallback couldn't get anywhere. The container's resolver doesn't know world.test, so db.world.test failed to resolve and the call came back as 502. That looked exactly like a correct deny. Even by IP, your Mac routes 100.64.0.0/10 into its own Tailscale interface, which has no such peer and would drop the packet. Only on a tailnet that the host itself belongs to does the fallback reach anything.

The fix in tsproxy/main.go

DialContext: func(ctx, network, addr) {
    host, port := net.SplitHostPort(addr)
    ip, err := peerAddr(ctx, host)   // look host up in lc.Status().Peer
    if err != nil { return err }     // "not a tailnet peer of this node"
    return s.Dial(ctx, network, ip:port)  // always a Tailscale IP
}

Result on the real tailnet: 9 of 9 checks pass. Calls to nodes that aren't peers fail in milliseconds. Calls to peers that the policy denies still time out, because those are silent drops inside the tailnet.

6. Netmaps: who gets told what

Control pushes each node its own netmap: only the peers the policy connects it to, with their keys and tags. Netmap size follows how widely a node can be reached, not the total node count. The example is a hub-and-spoke policy with 1,000 clients.

7. Assuming a role on the tailnet

Tailscale has no "assume role" step: tags are always on. You can still build one, because a role can be its own tailnet node. Your host keeps a low-privilege identity running all the time, and starts a second, ephemeral identity when it needs the stronger role.

8. A shared role proxy, with audit

A cleaner version of section 7. The admin role lives in one shared service, admin-proxy, and nobody else holds an admin credential. The policy decides who may reach it, which is the assumption policy. The proxy forwards requests as itself and adds who it is acting for. The target believes that header only from callers it trusts as forwarders.

9. Delegation: who vouches for "on behalf of"?

In section 8 the proxy itself asserts who it acts for, so the claim is only as honest as the proxy. With a signed delegation, the requester signs a short-lived assertion naming the proxy as its actor, and the backend evaluates policy on both identities. HR records show why both are needed: staff may read only their own record, and hr-admin may read all of them. In both lanes below staff-proxy is compromised.

10. Self-asserted key bindings, checked against the connection

An SDSI-style answer to section 9 with no CA and no authority. A node makes its own keypair and asserts "key K is me". Any party it connects to checks that assertion against the one fact it can't fake: the WhoIs identity of that WireGuard connection. From then on, that party attributes anything signed with K to the node, however the message arrives.

Wire format. Everything travels as HTTP headers. The client-sent ones deliberately don't start with X-Tailnet-, because ingress strips those as spoofable.

HeaderSent by → toContentReceiver checks
Tailnet-Key-Bindingclient → any hopself-signed JWS {id, key, t} (Ed25519)signature; id == WhoIs of the connection; cache thumbprint → id
X-Tailnet-Keyingress → own app (loopback)verified key thumbprintnothing: plain header inside the trust boundary
Tailnet-Assertionclient → via relays → targetJWS {sub, act, aud, exp} signed with the client's keykey known → sub; act == WhoIs caller; aud, exp
Tailnet-Binding-Witnessforwarding proxy → next hopJWS {binding: hash, observed: <WhoIs id>, t} signed with the proxy's keyproxy's key known first-hand; proxy trusted as a witness for names

Ephemeral keys. The key doesn't have to live long. A node can make a fresh keypair only when it needs to sign something, and send the message with its Tailnet-Key-Binding in the same request. The first hop checks the binding against WhoIs, verifies the signature and knows the message came from that node. The key is then thrown away, so nothing needs storing, nothing can be stolen later, and no cache goes stale: the key lives exactly as long as the assertion's exp.

What you give up is "register once, then accept by pigeon from anyone". With a longer-lived key, a target that saw the binding first-hand on an earlier connection can later verify messages relayed by a proxy it doesn't trust. With an ephemeral key, someone has to check the binding against WhoIs for this message. That's either the target itself (a direct connection) or a witness the target trusts. A target that only ever hears from relays trusts its witness in both cases, so for that target, ephemeral keys cost nothing. The middle ground is the proxy-certificate chain again: an ephemeral key signed by a longer-lived key that targets already know first-hand.
